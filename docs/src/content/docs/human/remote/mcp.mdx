The remote Worker can also act as a [Model Context Protocol](https://modelcontextprotocol.io) server. Agents connect to it over OAuth 2.1, so memory access follows the repository namespace instead of a shared bearer token.

> Only GitHub OAuth is supported for now.

The MCP endpoint is opt-in. Without configuration the REST API keeps working and MCP routes return `503` with a hint listing the missing variables.

## Enable the endpoint

1. Create a [GitHub OAuth app](https://github.com/settings/developers). The callback URL must be `https://<worker-url>/callback`.
2. Set the following variables when deploying the stack, for example in `remote-db/cloudflare/.env`:

   ```sh
   GITHUB_CLIENT_ID=your-github-oauth-app-client-id
   GITHUB_CLIENT_SECRET=your-github-oauth-app-client-secret
   COOKIE_ENCRYPTION_KEY=your-random-cookie-signing-secret
   ```

   Generate the cookie signing key with `openssl rand -hex 32`.

3. Redeploy:

   ```sh
   machine-memory remote provision
   ```

The variables are bound to the Worker as secrets. They are read once at worker startup; missing values keep the MCP routes disabled.

## Connect a client

Point an OAuth-capable MCP client at `https://<worker-url>/mcp`. The OAuth 2.1 flow handles client registration, dynamic client metadata, token issuance, and refresh tokens automatically.

- Authorization server metadata: `https://<worker-url>/.well-known/oauth-authorization-server`
- Protected resource metadata: `https://<worker-url>/.well-known/oauth-protected-resource`

On first connection the browser opens the authorization page: the client is registered, GitHub identity is verified, and the resulting tokens are scoped to the repositories granted.

## Tools

Read tools (`memory_query`, `memory_get`, `memory_list`) accept any `repository` slug — a wrong slug returns empty results and nothing is lost, so they can proceed without prior confirmation.

Write tools (`memory_add`, `memory_update`, `memory_delete`) require an exact `repository` slug and have no default. Call `list_repositories` first when the slug is not known from context.

| Tool                | Purpose                                                   |
| ------------------- | --------------------------------------------------------- |
| `list_repositories` | List all `owner/name` slugs that have stored memories     |
| `memory_query`      | Keyword, semantic, or hybrid search with filters          |
| `memory_get`        | Fetch one memory by numeric id                            |
| `memory_list`       | List recent memories with optional filters                |
| `memory_add`        | Create a memory (content, tags, context, type, certainty) |
| `memory_update`     | Update a memory's content or metadata by id               |
| `memory_delete`     | Delete a memory and its vector by id                      |

Every tool that accepts a `repository` argument expects it in `owner/name` form. Memories are stored in D1 and mirrored to Vectorize automatically.

Search modes mirror the CLI: `keyword` uses the D1 full-text index, `semantic` uses Vectorize embeddings, and `hybrid` merges both. The `status`, `memory_type`, and `certainty` filters accept the same enum values as the CLI.

### Write-scope confirmation

`memory_add` and `memory_delete` echo back the repository they wrote to as part of every successful response:

```json
// memory_add
{ "written_to": "owner/repo", "id": 42, "memory": { ... } }

// memory_delete
{ "deleted_from": "owner/repo", "id": 42, "deleted": true, "existed": true }
```

This makes a wrong-scope write visible in the conversation transcript rather than silently buried in a success response.
