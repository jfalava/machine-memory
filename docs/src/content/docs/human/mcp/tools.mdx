Read tools (`memory_query`, `memory_get`, `memory_list`) accept any `repository` slug — a wrong slug is harmless: `memory_query` and `memory_list` return empty results and `memory_get` returns a not-found message, so they can proceed without prior confirmation.

Write tools (`memory_add`, `memory_update`, `memory_delete`) require an exact `repository` slug and have no default. Call `list_repositories` first when the slug is not known from context.

| Tool                | Purpose                                                   |
| ------------------- | --------------------------------------------------------- |
| `list_repositories` | List all `owner/name` slugs that have stored memories     |
| `memory_query`      | Keyword, semantic, or hybrid search with filters          |
| `memory_get`        | Fetch one memory by numeric id                            |
| `memory_list`       | List recent memories with optional filters                |
| `memory_add`        | Create a memory (content, tags, context, type, certainty) |
| `memory_update`     | Update a memory's content or metadata by id               |
| `memory_delete`     | Delete a memory and its vector by id                      |

Every tool that accepts a `repository` argument expects it in `owner/name` form. Memories are stored in D1 and mirrored to Vectorize automatically.

Search modes mirror the CLI: `keyword` uses the D1 full-text index, `semantic` uses Vectorize embeddings, and `hybrid` merges both. The `status`, `memory_type`, and `certainty` filters accept the same enum values as the CLI.

## Write-scope confirmation

`memory_add` and `memory_delete` echo back the repository they wrote to as part of every successful response:

```json
// memory_add
{ "written_to": "owner/repo", "id": 42, "memory": { ... } }

// memory_delete
{ "deleted_from": "owner/repo", "id": 42, "deleted": true, "existed": true }
```

This makes a wrong-scope write visible in the conversation transcript rather than silently buried in a success response.
