After [enabling MCP](/docs/mcp/enable) and connecting a client to `/mcp`, these tools are available.

## Safety model

| Kind     | Tools                                                                                                                                       | Wrong `repository` slug                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Read     | `memory_suggest`, `memory_query`, `memory_get`, `memory_history`, `memory_list`, `tag_map_list`                                             | Empty or not-found; nothing lost        |
| Maintain | `memory_doctor`, `memory_stats`, `memory_gc`, `memory_coverage`                                                                             | Empty report; nothing lost              |
| Check    | `memory_verify`, `memory_diff`                                                                                                              | Not-found message; nothing lost         |
| Measure  | `memory_size`                                                                                                                               | N/A (no repository)                     |
| Discover | `list_repositories`                                                                                                                         | N/A                                     |
| Write    | `memory_add`, `memory_update`, `memory_restore`, `memory_deprecate`, `memory_delete`, `memory_delete_many`, `tag_map_set`, `tag_map_delete` | Required exact `owner/name`; no default |

Call `list_repositories` before writes when the slug is not certain. Derive `owner/name` from `git remote get-url origin` when it matches a known entry.

## Tool reference

| Tool                 | Purpose                                                                       |
| -------------------- | ----------------------------------------------------------------------------- |
| `list_repositories`  | List slugs with total, active, deprecated, and superseded counts              |
| `memory_suggest`     | File-scoped lookup: FTS over path terms + directory neighborhood              |
| `memory_query`       | Keyword, semantic, or hybrid search with filters                              |
| `memory_get`         | Fetch up to 100 memories in full by numeric `ids`; misses are `missing_ids`   |
| `memory_history`     | List complete previous revisions, newest first, with the current update count |
| `memory_list`        | List memories with filters and offset pagination                              |
| `memory_doctor`      | Audit duplicates, status expiry, types, tags, and refs                        |
| `memory_stats`       | Summarize status, type, certainty, tag, and age distributions; index status   |
| `memory_gc`          | Preview expired status memories; never mutates                                |
| `memory_verify`      | Check an inferred fact against a memory (consistent / conflict)               |
| `memory_diff`        | Diff proposed content against a memory (terms added / removed)                |
| `memory_size`        | Measure a memory against the 2,000-byte limit without writing                 |
| `memory_add`         | Create a memory (or upsert via `upsert_match`)                                |
| `memory_update`      | Update content or metadata by id (or `match`)                                 |
| `memory_restore`     | Restore a reviewed revision in place, refusing a stale update count           |
| `memory_deprecate`   | Mark up to 100 explicit ids deprecated or superseded, preserving history      |
| `memory_delete`      | Permanently delete one memory and its vector                                  |
| `memory_delete_many` | Permanently delete up to 100 explicit ids and their vectors                   |
| `tag_map_list`       | List the tag map; with `paths`, the tags those files would get                |
| `tag_map_set`        | Set the tags of one path prefix, replacing the tags it had                    |
| `tag_map_delete`     | Remove one path prefix; reports `deleted` or `not_found`                      |
| `memory_coverage`    | List the directories no active memory is about, and count the rest            |

Every tool that takes `repository` expects `owner/name`. Rows live in D1; embeddings sync to Vectorize on write. `memory_query`, `memory_list`, and `memory_suggest` accept a `tags` substring filter alongside `status` / `memory_type` / `certainty`.

### Read results

`memory_get`, `memory_query`, `memory_list` and `memory_suggest` all return an
object that starts with `repository` and `count` and holds the memories in
`results`. `memory_get` takes `ids` and never fails on a missing id: it lists
the id in `missing_ids`, and in `found_elsewhere` when another repository
holds it.

### Who wrote a memory

`memory_add`, `memory_update` and `memory_deprecate` take an optional
`source_agent`: the agent and its thread or session, such as `amp:T-1234`. It
is stored as `source_agent` on a new memory and as `last_updated_by` on every
write. When it is omitted, the write is attributed to the authenticated GitHub
user as `mcp:<login>`.

### Pagination and repository counts

`memory_list` and `list_repositories` return `count`, `total_count`, `offset`, `limit`, and `has_more`. Continue with `offset + count` while `has_more` is true. `list_repositories` entries include `slug`, `total`, `active`, `deprecated`, and `superseded`, so a cleanup can be scoped without blind per-repository queries.

### Maintenance

- `memory_doctor` audits active memories and returns typed findings with every involved id. Findings are suggestions: review them semantically before writing.
- `memory_stats` reports aggregate status, type, certainty, tag, and age data for one repository. Its `index` field reports how many records are `pending`, `retrying` or `parked` in the semantic index, how many are `unindexed` (active records whose vector predates the current index), and the failures grouped by error.
- `memory_gc` is always a dry run. It returns active status memories whose `expires_after_days` window has elapsed.
- `memory_deprecate` accepts `ids` and optional `superseded_by`. It preserves the records and re-syncs their vector metadata.
- `memory_delete_many` accepts one to 100 explicit `ids`. It is permanent and echoes `deleted_from`, `deleted_ids`, and `not_found`.
- `memory_coverage` takes `directories`, one to 2,000 directory paths relative to the repository root, because the server cannot walk a checkout. It returns `checked`, `uncovered_paths`, `covered_paths` (the number of active memories per covered directory) and `tag_distribution`. A memory covers a directory when its content, context or refs name a path in it, or when it carries a tag the tag map gives to the directory or to a prefix inside it; see [coverage](/machine/coverage).

### Tag map

The tag map gives memories about one directory the same tags. `tag_map_set` (`{ repository, path_prefix, tags }`) stores the tags of a prefix, and a prefix covers the path itself and everything under it. `memory_add` with `paths` then adds the tags of every prefix those paths fall under. `tag_map_list` returns `mappings`; with `paths` it also returns `tags`, `matches` and `unmatched_paths`, which is the CLI's `tag-map suggest`. `tag_map_delete` (`{ repository, path_prefix }`) reports `deleted` or `not_found`. Changing the map leaves the tags of existing memories as they are.

### Suggest

`memory_suggest` ports the CLI `suggest` command for the pre-edit scan. Pass comma-separated `files` plus an optional extra `query`; it returns the derived path terms, the directory neighborhood (`tags` / `paths` hints), `no_strong_match`, and scored results. A result is `strong` only when the memory names a suggested file by full path or specific file name. Manifests and lockfiles are searched by directory, not by name, and listed in `generic_files`.

### Verify and diff

`memory_verify` (`{ repository, id, fact }`) and `memory_diff` (`{ repository, id, content }`) port the CLI `verify` / `diff` commands (term similarity plus negation check). Use them before `memory_update` when an inference may conflict with a stored memory.

### Writes

`memory_add` refuses a memory that an active one already states (text overlap of 0.78 or more) and names that memory. Pass `update_id` to replace that memory's content, keeping the fields you omit, or `create_new: true` when you read the existing memories and this is a different fact. `upsert_match` finds the target by topic instead (with `upsert_threshold`, default `rank_score` 50, alongside `text_overlap` ≥ 0.62): a strong match updates in place, no match creates a record, and a weak match is refused with up to three candidates, each with `rank_score`, `text_overlap` and `shared_identifiers`. New records echo `related`, the active memories that strongly match them, when there are any.

`memory_update` targets `id` or `match` (best active full-text hit, echoed back as `matched`); only provided fields change, so omitting `content` changes only metadata. `add_tags`, `remove_tags`, `add_validation_gaps` and `remove_validation_gaps` change part of a list; `tags` and `validation_gaps` replace it.

Replacing content, through `memory_update`, `update_id` or a strong `upsert_match`, is refused when it drops a path, flag or symbol that no other active memory mentions, or shares almost nothing with the stored content. The error names what would be lost. Carry it over, add a new memory when this is a different fact, or pass `allow_drop: true` when the detail is obsolete. A content or status change also returns `dropped` (identifiers and sentences the new content lost) and `review_candidates`: up to five other active memories that cite the changed memory by id (`cites: true`) or share at least two paths, flags or symbols with the changed text (`shared_identifiers`). They are candidates: read each one and change it only when it relies on what changed. An update that only adds text lists none. `memory_deprecate` returns `review_candidates` too, and `memory_diff` returns `dropped` before anything is written. It also accepts `expires_after_days` (status memories only). Prefer `memory_deprecate` for dedicated deprecation and supersession workflows.

### History and recovery

`memory_history` takes `{ repository, id, limit?, offset? }` and returns complete
previous snapshots, newest first. It includes `current_update_count` and the
usual pagination fields. Review a snapshot, then call `memory_restore` with
`{ repository, id, revision_id, expected_update_count }`. Set
`expected_update_count` to the response's **`current_update_count`**, not the
historical row's count. A newer write causes a conflict instead of being overwritten.

Restore preserves the ID and repository, increments the current update count,
refreshes `updated_at`, and marks `last_updated_by` as `restore`. It restores
the other metadata, including refs, replacement, and expiry; status expiry
starts from the fresh update time. The replaced state becomes another history
entry, so a restore can itself be undone.

Snapshots are never embedded or included in memory searches. Only the restored
canonical row queues vector synchronization: active rows are embedded, while
inactive rows have their vectors removed. No migration-time reindex is needed.
History starts at migration `0004`; earlier overwrites cannot be recovered.
There is no automatic pruning, and existing import/export and local-to-remote
transfers do not carry history. **Permanent deletion also purges history.**
See [history and restore](/machine/history) for CLI usage and constraints.

### Search

`memory_query` `mode`:

| Mode       | Behavior             |
| ---------- | -------------------- |
| `keyword`  | D1 full-text index   |
| `semantic` | Vectorize embeddings |
| `hybrid`   | Merge both (default) |

Filters `status`, `memory_type`, and `certainty` use the same enums as the CLI.

Search results and full rows include `evidence` and `validation_gaps`. Neither is embedded, so they do not affect semantic search or the size budget.

`memory_query` returns `{ count, no_strong_match, results }`. Each result includes `score`, which only ranks within the response, plus absolute relevance fields: `match_strength` (`strong`, `weak`, or `none`), `term_coverage`, `exact_matches`, and `matched_terms` with `matched_in` (the fields that hold them). A status memory past its expiry is left out unless `memory_type` is `status`. Strong results come first. When `no_strong_match` is true, treat the results as loosely related candidates. The thresholds match the CLI; see [query match strength](/machine/query#match-strength).

### Writes

Typical fields on `memory_add` / `memory_update`:

- `content` (required on add) — put commands, paths, and identifiers in the first sentence
- `tags` — comma-separated, e.g. `area:cli,topic:backend,kind:decision`
- `paths` (add only) — the files the memory is about; adds the tags of every [tag map](/machine/tag-map) prefix they fall under, and the result lists them in `path_tag_matches` and the paths no prefix matched in `unmatched_paths`
- `context` — optional supporting text
- `memory_type` — `decision`, `convention`, `gotcha`, `preference`, `constraint`, `reference`, `status`
- `certainty` — `verified`, `inferred`, `speculative`; `verified` requires a non-empty `evidence`
- `evidence` — array of `user_requirement`, `observed_implementation`, `verified_mechanism`, `tested_behavior`; on update it replaces the stored array and `[]` clears it
- `validation_gaps` — array of up to 16 short strings naming what is still unconfirmed, such as user intent or untested platforms
- `status` — `active`, `deprecated`, `superseded_by`
- `expires_after_days` — only valid when `memory_type` is `status`

## Size limit

A memory's embedded text (content, plus `Tags:` and `Context:` lines when set) is at most 2,000 UTF-8 bytes. Memory type, status, and certainty are not counted. The CLI enforces the same limit.

- **`memory_size`** — measures without writing; a report over the limit sets `isError: true` and includes `over_by_bytes`
- **`memory_add` / `memory_update`** — refuse a memory over the limit before any D1 write; the error says how many bytes to remove

Call `memory_size` before long writes.

## Agent workflow (short)

1. `list_repositories` if the slug is unknown
2. `memory_suggest` (known files) or `memory_query` / `memory_list` before code changes
3. `memory_get` with the `ids` of the records you will rely on
4. `memory_verify` / `memory_diff` when an inference may conflict
5. `memory_size` when content may be large
6. `memory_doctor` / `memory_stats` / `memory_gc` during maintenance
7. `memory_add` (prefer `upsert_match`) / `memory_update` (prefer `match`) for durable outcomes
8. `memory_deprecate` for obsolete records; use permanent delete tools only when intended

Install that checklist into the repo with [Init](/docs/mcp/init).
