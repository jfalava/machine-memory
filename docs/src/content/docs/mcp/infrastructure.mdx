MCP runs on the same remote stack as the CLI’s `--remote` backend. You deploy it once, then optionally enable MCP OAuth on top.

## What gets created

The [Alchemy stack](https://github.com/jfalava/machine-memory/tree/master/remote-db/cloudflare) provisions:

| Resource           | Role                                                                        |
| ------------------ | --------------------------------------------------------------------------- |
| Worker API         | Authenticated REST (`/query`, …) and, when configured, MCP (`/mcp`) + OAuth |
| D1 database        | Canonical memory rows and FTS                                               |
| Vectorize index    | Semantic embeddings                                                         |
| Workers AI binding | BGE embeddings for writes and semantic search                               |
| KV (OAuth)         | Authorization state and tokens when MCP is enabled                          |

Source of truth for names and bindings: `remote-db/cloudflare/` (`alchemy.run.ts`, `src/config.ts`).

## Prerequisites

- A Cloudflare account that can create Workers, D1, Vectorize, Workers AI, and KV
- Cloudflare credentials available to the deploy process (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, or Alchemy login)
- Bun, to run the stack from this monorepo or via the CLI provisioner

## Deploy with the CLI

From a machine that can reach Cloudflare and the monorepo’s Alchemy stack:

```sh
machine-memory remote provision
```

That command:

1. Runs `alchemy deploy` for the remote-db stack
2. Generates or reuses a Worker token for the REST API
3. Stores URL + token in the OS keychain (for CLI `--remote`)

### Names and defaults

| Option            | Environment variable        | Default                    |
| ----------------- | --------------------------- | -------------------------- |
| `--stack-name`    | `MACHINE_MEMORY_STACK_NAME` | `machine-memory-remote-db` |
| `--database-name` | `MACHINE_MEMORY_DB_NAME`    | `machine-memory-db`        |
| `--api-name`      | `MACHINE_MEMORY_API_NAME`   | `machine-memory-api`       |

Flags override env vars; stored remote credentials override defaults next.

After provision, the Worker URL looks like:

```text
https://machine-memory-api.<account>.workers.dev
```

REST clients and the CLI use `/query` (normalized by the CLI). MCP clients use `/mcp` on the same host after [Enable MCP](/mcp/enable).

## Deploy the stack directly

From the monorepo:

```sh
cd remote-db/cloudflare
# optional: copy .env.example → .env and fill values
CI=1 bun run deploy
# first time against an existing account resource set:
# CI=1 bunx alchemy deploy --yes --adopt
```

Useful env vars (see `remote-db/cloudflare/.env.example`):

```sh
MACHINE_MEMORY_DB_TOKEN=...
MACHINE_MEMORY_STACK_NAME=machine-memory-remote-db
MACHINE_MEMORY_API_NAME=machine-memory-api
MACHINE_MEMORY_DB_NAME=machine-memory-db
MACHINE_MEMORY_VECTOR_INDEX_NAME=machine-memory-v1
MACHINE_MEMORY_OAUTH_KV_NAME=machine-memory-oauth-kv
```

MCP OAuth secrets are optional at this stage. Without them the Worker still serves REST; MCP routes stay disabled until you [enable the endpoint](/mcp/enable).

## Already have a Worker?

Point the CLI at it with [`remote setup`](/human/remote/setup). MCP still needs the OAuth secrets on that same Worker deployment.

## Sandboxed / no keychain

For CLI remote access without OS keychain, put credentials in a repo-root `.env` — see [Sandboxed keychain access](/human/remote/keychain-access). MCP clients do not use that token; they use OAuth to `/mcp`.
